哈希长度扩展攻击

SM3 并不是一次性把所有数据算完的，而是分块处理（每块 64 字节）。前一个块运算的结果（即内部状态 IV），会作为下一个块的初始向量（Input）。服务器给的 token，本质上就是处理完 Secret 后，SM3 算法停留在内存里的最后状态。如果能拿到这个状态，就可以在这个状态的基础上继续往后算

Secret 长度 = 64 字节。Original Token = SM3(Secret)。

伪造 SM3(Secret + Padding + "REDROCK")。

Flag 在 flag_buf，还有一个printf（user_buf)格式化字符串漏洞

user_buf: rbp-0x90，

flag_buf: rbp-0x50，相差0x90 - 0x50 = 0x40字节。8个内存单元。因此 flag_buf 距离 user_buf 的为 8个栈单元

以AAAA为做标记，发送 payload，从程序输出中找到AAAA对应的十六进制标识（0x41414141），以此确定user_buf的格式化偏移n；算出flag_buf的格式化偏移为n+8；随后使用%flag_offset$p读取十六进制原始数据；提取小端序解码 Hex 数据即可

拯救大兵call1ng

No NX栈可执行 ，

程序通过 printf(format, buf) 打印了 buf 的真实栈地址

read(0, buf, 0x40) 读取了 64 字节，而 buf 只有 16 字节，存在溢出。可以把返回地址 改写成 Shellcode 所在的地址。 根据栈布局：[Buf (16)] + [RBP (8)] + [Ret (8)] + [Shellcode (剩余空间)]。 Shellcode 实际上被放在了 Ret 之后的位置。 所以目标地址 = A + 16 + 8 + 8-> 泄露地址** + 32**。

read 总共读 64 字节。 Padding(24) + Ret(8) 占用了 32 字节。 剩下 64 - 32 = 32 字节给 Shellcode。 使用 23 字节的短 Shellcode。

梦

checksec一下

NX 开启，Canary 开启，No PIE,read(0, v1, 128)，v1 大小 36 字节

程序内包含 /bin/sh 字符串，但没有 system 函数

由于无法直接泄露 Canary，但可以多次尝试连接

Canary 为 4 字节，最低位固定为 \x00。剩余 3 字节是随机的。保持 Offset 不变，从第 2 个字节开始，尝试 0x00-0xff。若程序不报错则对。逐位爆破出完整 Canary，程序没有 system 函数，构造 execve("/bin/sh", 0, 0) 系统调用

栈的结构是：[缓冲区] -> [Canary] -> [Saved EBP] -> [Ret Addr]。v1 开始于 ebp - 0x28 (即 40 字节)。Canary 位于 ebp - 0x4 (4 字节)。

offset = 40 - 4 = 36字节

高处不胜寒

缓冲区 buf 大小：48 字节。

read 读取大小：55 字节。剩余：55 - 48 = 7 字节。

要覆盖返回地址，需要 $$48 (\text{buf}) + 8 (\text{rbp}) = 5$$ 字节

但只有 7 字节溢出

利用 main 函数结尾的 leave; ret 指令，题目给出的 printf 获取 buf 在栈上的真实地址（设为 Target_Addr）。

通过 7 字节溢出，将栈上的 Saved RBP 修改为 Target_Addr

当 main 执行 leave时：

mov rsp, rbp：此时 RBP 已经是我们伪造的地址了，所以 RSP (栈指针) 跳到了我们的 buf

payload：

偏移 内容 说明
00-07 AAAAAAAA 填充，被 leave 中的 pop rbp 消耗
8-15( ret_addr 对齐，main返回RSP+8，修复system6字节对齐问题
16-23 backdoor 后门地址
24-47 padding 填充剩余空间
48-54 buf_addr 覆盖 Saved RBP，将栈劫持回buf

64位 Linux 的 system() 函数要求调用时栈必须 16字节对齐（地址尾数是 0）。如果我们在栈迁移后直接跳去 backdoor，栈尾数是 8，会导致程序崩溃。但是可以先跳到 0x40101a (执行 ret)。因为ret 指令执行一次 pop 操作。栈指针 (RSP) 往上移动 8 字节。这样就能对齐，再跳去 backdoor，system() 就能正常运行了。

得到ret_addr = 0x40101a

密文

使用 0x0E 对 密文 进行异或解密得到的是乱码

仔细看这段代码

当执行 INT 21H （输出字符）时，AL 寄存器往往会被修改为最后输出字符的 ASCII 码。 由于宏的最后一步是输出换行符 0x0A，在宏执行结束后，AL 的值实际上从 0x0E 变成了 0x0A。

因此，MOV BH, AL 执行时，实际的密钥是 **0x0A**。
